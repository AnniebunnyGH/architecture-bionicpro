# Архитектурные диаграммы BionicPRO (C4 Container)

## Задание 1 — Повышение безопасности и управление учётными данными

Файл диаграммы: [task1_security_c4.drawio](./task1_security_c4.drawio)

### Ключевые архитектурные решения

1. **Унификация доступа (SSO) и локальное хранение ПДн/медицинских данных (152-ФЗ, GDPR):**
   - В качестве единого центра аутентификации (SSO / Identity Provider) используется **Keycloak**.
   - Учётные данные и персональная/медицинская информация пациентов хранятся **строго в контуре страны представительства** (региональный OpenLDAP / Active Directory + региональная БД ПДн и медицинских данных).
   - Keycloak подключается к региональным каталогам через **LDAP User Federation (LDAPS)** без репликации персональных данных в центральную БД. Во внутренних сервисах и БД телеметрии BionicPRO используется обезличенный идентификатор (`sub` / UUID).
2. **Безопасная схема работы с access- и refresh-токенами (BFF — Backend for Frontend):**
   - Между клиентскими приложениями (Web SPA / Mobile) и Keycloak / API внедрён **BFF (Auth Gateway)**, выступающий как Confidential OAuth 2.0 Client.
   - BFF выполняет обмен кода на токены по **OAuth 2.0 Authorization Code Flow + PKCE (S256)**, сохраняет `access_token` и `refresh_token` в зашифрованном серверном хранилище **Redis (Session Store)** и выдаёт клиенту только `HttpOnly; Secure; SameSite=Strict` session cookie.
   - Токены, полученные от IdP, **никогда не передаются на фронтенд** и недоступны из JavaScript (защита от XSS-кражи токенов). При вызове внутренних API BFF самостоятельно подставляет `Authorization: Bearer <access_token>` и прозрачно обновляет токен по `refresh_token`.
3. **Поддержка внешних удостоверяющих служб разных стран (Identity Brokering):**
   - Keycloak работает как **Identity Broker** (OIDC / SAML 2.0), что позволяет подключать национальные и глобальные IdP: например, **Яндекс ID / ЕСИА (Госуслуги)** в РФ и **Google / Apple / eIDAS** в ЕС и других странах, выпуская унифицированный внутренний JWT с RBAC-ролями (`prothetic_user`, `user`, `administrator`).

## Задание 2 — Архитектура сервиса отчётов и ETL-пайплайна

Файл диаграммы: [task2_reports_c4.drawio](./task2_reports_c4.drawio)

### Ключевые архитектурные решения

1. **Разделение OLTP и OLAP нагрузок:**
   - Операционные базы (`CRM DB` и `Telemetry DB` на PostgreSQL) больше не нагружаются тяжёлыми аналитическими запросами отчётов и ML-инструментов.
   - Для аналитики и формирования отчётов развёрнута колоночная OLAP-база **ClickHouse**.
2. **ETL-процесс по расписанию на Apache Airflow:**
   - DAG `prosthesis_reports_etl` запускается по расписанию (`0 * * * *`), извлекает актуальные данные о клиентах и протезах из `CRM DB` и сырую телеметрию миодатчиков из `Telemetry DB` за окно до момента выполнения.
   - В ClickHouse данные объединяются и агрегируются в готовую витрину **`user_reports_mart`** (`Engine = ReplacingMergeTree(updated_at)`, `PARTITION BY toYYYYMM(report_date)`, `ORDER BY (keycloak_username, report_date, prosthesis_id)`), что обеспечивает мгновенный доступ по конкретному пользователю без вычислений в реальном времени.
   - По завершении расчёта DAG обновляет таблицу **`etl_watermarks`** с границами успешно обработанного периода (`min_processed_date`, `max_processed_date`).
3. **Сервис отчётов (Reports API на TypeScript) и контроль доступа:**
   - Валидирует JWT-токен по **JWKS** Keycloak (неаутентифицированные запросы отклоняются с `401`).
   - Проверяет RBAC-роль `prothetic_user` (`403` для пользователей без прав).
   - Гарантирует доступ **только к собственному отчёту**: идентификатор пользователя извлекается исключительно из верифицированного токена (`preferred_username`), а попытка запросить чужого пользователя отклоняется с `403 Forbidden`.
   - Проверяет запрашиваемый период по **`etl_watermarks`** в ClickHouse: запрос данных за ещё не обработанный Airflow период отклоняется с `422 Unprocessable Entity` и подсказкой доступного диапазона дат.
